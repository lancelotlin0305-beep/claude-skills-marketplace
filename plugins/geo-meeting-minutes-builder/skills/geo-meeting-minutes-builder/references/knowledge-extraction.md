# 知識萃取(獨立產出,詢問後才做)

知識萃取**不寫進會議記錄**,而是獨立產出一份 HTML 檔(含 SVG 圖表),
規格見 `knowledge-html-spec.md`,模板見 `assets/knowledge-extraction-template.html`。

## 1. 觸發時機(重要)

| 情況 | 做法 |
| --- | --- |
| 使用者**一開始就說**要知識萃取 / 知識傳承 / 技能傳承 / 「把重點知識整理出來」 | 直接做,會議記錄與知識檔一併產出 |
| 使用者**未提及** | **先產會議記錄,交付後再問一句**,得到肯定答覆才做 |

詢問的措辭要具體、可判斷,不要問空泛的「還需要什麼嗎」。依會議實際內容給出誘因:

> 這場會議中我注意到有 7 處可留存的知識點(客戶說明的法規申報期限、
> 他們現行的三段簽核流程、以及一段關於前次系統失敗原因的說明)。
> 要不要另外產一份知識萃取檔?會是獨立的 HTML,含分類卡片與知識分布圖。

**沒有值得留存的知識點時,就不要問** —— 照實說「這場會議以進度確認為主,沒有適合留存的知識點」。
硬問一句會讓使用者每次都要拒絕一遍。

**產出會議記錄的同時不預先萃取。** 不要「先做好放著等他要」—— 那會拖慢會議記錄的交付,
而會議記錄才是使用者當下真正需要的東西。

## 2. 五種分類

每張卡片標一個分類。分類決定它日後會被誰、在什麼情境下找出來用。

| 代號 | 分類 | 內容 | 主要來源 |
| --- | --- | --- | --- |
| `DOM` | 領域知識 | 產業慣例、法規要求、業務規則、專有名詞的實際意義 | **對外會議為主** |
| `TEC` | 技術知識 | 工具、架構、實作細節、參數、除錯經驗 | 內部技術分享為主 |
| `PRO` | 流程知識 | 誰做什麼、依序怎麼走、條件分岔、例外處理 | 兩者皆有 |
| `ACC` | 對象脈絡 🔒 | 組織結構、決策鏈、偏好與雷區、歷史包袱 | **僅對外會議**,限閱 |
| `PRA` | 應對經驗 | 異議處理、說明方式、談判取捨、除錯思路 | 對外會議的攻防過程 |

ID 格式 `KP-DOM-01`、`KP-TEC-03`,**專案內連號**,跨會議延續(見 `cross-meeting.md`)。

## 3. 卡片必要欄位

- **標題** —— 名詞短語,講清楚是什麼,不要用「關於 X 的討論」這種標題
- **分類**(五選一)
- **是什麼** —— 一到兩句定義
- **為什麼重要 / 解決什麼問題**
- **關鍵細節** —— 步驟、參數、指令、法條號、期限規定。**照抄不改**
- **踩過的坑 / 注意事項** —— 講述者提到的失敗經驗或警告,**這欄最有價值**
- **來源** —— 時間戳 `[00:34:12]` 或 `[手寫摘要 p.2]` / `[簡報 p.12]`
- **講述者** —— 姓名(單位)
- **信心** —— 高 / 中 / 低

## 4. 抓取訊號

**通用**
- 講述者花超過 2 分鐘解釋同一件事
- 「這個很重要」「大家注意」「我之前踩過」「你們要小心」
- 有具體數字、參數、指令、版本號、法條、期限規定 → **照抄不改**
- 有人問「為什麼」,而回答不只一句話

**對外會議特有(最容易被漏掉)**
- 「因為法規 / 總公司規定 / 稽核要求⋯」→ `DOM`,把來源規定名稱一併記下
- 「我們以前做過,結果⋯」→ `DOM` + 踩坑欄位,價值極高
- 客戶描述現行作業步驟 → `PRO`,同時產流程草稿
- 客戶反覆問同一類問題 → `DOM`,代表這是常見誤解,值得做成標準說明
- 客戶對某做法反應強烈(排斥或特別在意)→ `ACC` 🔒
- 客戶提到誰要簽核、誰會反對、誰說了算 → `ACC` 🔒
- 我方的某套說法效果好 → `PRA`,可複用
- 客戶問倒我方的問題 → 進「延伸問題」,代表我方領域理解不足

**不要收**
- 純背景閒聊、與工作無關的類比
- 網路查得到、且會中沒有加入任何在地經驗的通識
- 為了湊數量而把常識寫成知識點

**三張紮實的卡片勝過十張廢話。** 寧可某場會議一張卡都沒有。

## 5. `ACC` 對象脈絡卡的紀律

內容通常是:「王處長是實際決策者」「他們對 X 廠商有陰影」「總經理下週才回國」。
**真實有用,但外流後果嚴重。**

- 一律標 🔒,在 HTML 中預設可一鍵隱藏(供簡報 / 螢幕分享時使用)
- 產對外版時**整段移除**,不是把關鍵字塗黑 —— 塗黑後上下文往往還是推得出來
- 用**中性、可佐證的措辭**記錄事實與來源,不寫人身評價
  - ✓ 「李經理表示需經王處長核可 `[00:22:10]`」
  - ✗ 「李經理沒有實權」
- 純屬記錄者推測的部分,標「記錄者觀察」與會議事實分離

## 6. 流程草稿(`PRO` 的延伸)

會中談到流程性內容時,在知識檔中另產流程草稿:

```
觸發:什麼情況下啟動
參與角色:
步驟:
  1. [角色] 動作 → 產出
  2. [角色] 動作 →(判斷條件)→ 分支 A / 分支 B
結束條件:
來源:[時間戳]
待確認 ⚠️:逐字稿沒講清楚的環節,逐條列
```

產完主動問:「這個流程要不要轉交 `geo-bpmn-flow-builder` 畫成正式流程圖?」
使用者說要才呼叫 `geo-bpmn-flow-builder` skill 並依循。**不自動接續。**

流程有環節沒講清楚時**照實留白並列進待確認**,不要用常識補完 ——
補出來的流程圖看起來完整,但畫的是想像中的流程,拿去傳承會傳錯。

## 7. 關鍵對話(原文保留)

需要保留原文而非改寫的場合:

- 問答攻防中,問題本身問得好
- 講述者的判斷準則(「我通常會看 X 再決定 Y」)
- 對某技術 / 做法的評價與取捨理由
- 現場的反對意見與辯論 —— **不要只留贏的一方**
- 客戶對需求的原始描述(改寫容易失真,後續拆需求時要回頭看原話)

## 8. 模式 B(無逐字稿)的知識萃取

只有手寫摘要時仍可做,但:

- 「關鍵細節」只填摘要中實際寫到的,**不得依常識補完**
- 信心一律標「中」以下
- 無時間戳 → HTML 中的知識分布時間軸**整塊省略**(見 `knowledge-html-spec.md`)
- 缺漏細節逐條寫進「待補問」,註明「原會議有講但筆記未記錄」

**趁記憶還在時補問,是模式 B 唯一的救援機會** —— 交付時提醒使用者一次。

## 9. 回寫待釐清清單(不可略過)

知識萃取過程中發現的缺漏(參數值未記錄、法規名稱不確定、流程環節不明),
要**回寫進會議記錄的「待釐清清單」節**,類型填「知識點細節缺漏」,
並將會議記錄版本推進一版(v1 → v2),在版本記錄表增列。

知識檔本身也列一份「待補問」摘要,但**權威清單在會議記錄裡** ——
避免兩份文件各有一半待辦,使用者不知道要看哪份。
