# 輸入處理:收件、判模式、前置索取

## 1. 先盤點手上有什麼

逐一確認下列項目,**列一張清單給使用者看**,再決定走哪個模式:

| 項目 | 用途 | 缺了會怎樣 |
| --- | --- | --- |
| 轉錄逐字稿(txt/md/docx/srt/vtt) | 模式 A 的事實依據 | 降級走模式 B |
| 出席者名單(姓名/單位/職稱) | 講者對應 | 模式 A 無法對回真人,必須索取 |
| 會議基本資料(日期/時間/主題/主持人) | 期限換算、檔名、表頭 | 期限無法絕對日期化 |
| 手寫摘要 / 現場筆記(文字或照片) | 重點指引、補逐字稿聽不清處 | 模式 B 無法成立 |
| 簡報 `.pptx` 或截圖 | 內部會議的頁碼對照 | 無法做簡報對照表 |
| 專案術語表 | 校正 ASR 錯字 | 專有名詞會殘留天書 |
| 前次會議記錄 | 模式 C 跨會議追蹤 | 無法產進度回顧 |
| 參考資料(規格、報價、既有文件) | 佐證與背景 | 部分脈絡缺失,標註即可 |

缺關鍵項目時**一次問齊**,不要一輪問一項。

## 2. 音檔 / 影片的轉錄(使用者給音檔 / 影片時)

本 skill 不直接轉錄。給兩條路,讓使用者選:

**路線一:轉交 `geo-transcribe-minutes` 轉錄(建議,品質最好)**
呼叫該 skill 產出帶時間戳的逐字稿後,回到本 skill 以模式 A 接手。**正式交接物**:
`segments.json`、`transcript_raw.txt`(引擎原樣、簡轉繁已由對方完成)、術語表、
會議基本資料(日期 / 出席者名單)、引擎名(含時間戳精度 —— Gemini 為分:秒級近似值,
記入逐字稿 MD 表頭「轉錄來源」欄)、輸出資料夾(本 skill 產出放進同一資料夾)。
**轉交而來時先讀交接資訊,已有項目不再向使用者索取**(§1 盤點表同理)。
轉交前講清楚引擎差異讓使用者選:雲端引擎(Gemini / Groq / ElevenLabs / OpenAI)快而準
**但音檔會上傳**;本地引擎(faster-whisper / SenseVoice)離線、機密錄音不出機器。
講者分離(diarization)視引擎而定 —— Gemini / ElevenLabs 有,Groq / 本地預設沒有,
沒有時講者對應改依 `transcript-cleanup.md` §2 的推斷規則並照實標信心。

使用者已有現成轉錄管道時不必堅持轉交:會議平台內建(Teams / Zoom / Google Meet)、
線上服務(Notta、雅婷逐字稿等)皆可,匯出時**保留時間戳與 Speaker 標籤**
(`.srt` / `.vtt` / 帶時間戳的 `.txt`)。不要幫使用者選外部服務商 ——
涉及資料上雲,由使用者依保密等級自行決定。

**防禦**:若拿到的輸入是其他工具的「順稿版 / 整理版」而非原始轉錄,
引用原話處一律標註「來源為整理稿,非原話」—— 整理稿的措辭可能已被改寫。

**路線二:直接走模式 B**
只用手寫摘要 + 簡報 + 參考資料產出會議記錄。說清楚代價:
沒有原文可回溯,決議與待辦的來源標註只能到「摘要第幾點」的粒度,信心等級整體較低,
且無法產出逐字稿 MD。適合會議短、筆記完整、或音檔已遺失的場合。

## 3. 術語表

開工前問一句:「這個專案有沒有常出現的專有名詞、系統代號、人名縮寫?」
拿到就建成對照表放在逐字稿 MD 的表頭區,並在整理逐字稿時全域校正。
沒有的話,從逐字稿裡把**高頻可疑詞**挑出來(明顯不成詞、音近技術名詞的),
列進待釐清清單請使用者確認,**不要自己猜著改**。

常見 ASR 中文誤譯樣態(僅供辨識,判斷仍須看上下文):
英文技術詞被音譯、公司內部代號被拆成無意義字串、數字與單位黏連、英文縮寫被拼成同音中文。

## 4. 敏感資訊

掃描下列類型並**在會議記錄中以 `🔒` 標記**,不刪除:

報價 / 成本 / 毛利、薪資與人事評價、個資(身分證、電話、住址、私人 email)、
未公開的商業條件、對第三方的負面評價。

知識萃取的 `ACC`(對象脈絡)卡片一律視為敏感,規則見 `knowledge-extraction.md` §5。

標記後主動問一句:「這份記錄要外發嗎?要的話我可以另產一份把 🔒 段落抽掉的對外版。」
使用者說要,才產 `..._會議記錄_對外版_v<n>.md`。**不主動生成,也不主動刪。**

對外版的移除範圍:所有 🔒 標記段落、`ACC` 分類的整節、待釐清清單中涉及內部判斷的項目。
移除是整段拿掉,不是把關鍵字塗黑 —— 塗黑後的上下文往往還是推得出來。

## 5. 會議類型研判

依下列訊號判斷,產出前用一句話確認:

- **對外訊號**:出現客戶 / 甲方 / 廠商稱謂、報價與合約用語、「我們這邊會⋯你們那邊⋯」的雙方句式、
  需求確認與驗收語言、簡報式的單向說明後接 Q&A。
- **內部訊號**:同公司同事互稱、技術實作細節、教學 / 分享型獨白、工具與流程討論、無合約商務語言。
- **混合**:對外會議後段轉入內部檢討,或內部會議中段客戶臨時加入。兩套章節都出。

研判不確定時,**直接問**,不要硬套。套錯結構的會議記錄比晚十秒問一句糟糕得多。

## 6. 長逐字稿的分段策略

兩小時會議常有 3～5 萬字。超過一次可處理的量時:

1. **先掃全文標議題邊界** —— 只讀出「第幾分鐘換到什麼話題」,產一份議題索引
2. **依議題分段精讀** —— 每段各自萃取決議 / 待辦 / 待議,保留時間戳
3. **合併去重** —— 同一件事在不同段落反覆出現時,以**最後一次拍板的版本為準**,
   並在來源標註列出所有相關時間戳(例:`[00:22:10] [01:05:33 修正]`)

**去重時特別注意反轉**:會議常見「前面說要做、後面又說算了」。合併階段必須檢查每條決議
在後續段落有沒有被推翻,漏掉就會產出完全相反的記錄。
